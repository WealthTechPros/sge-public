# Cascade check mechanisms (C4 sub-check, C5, C9, C10, C14, C19, C20, C21, C36, C39, composite)

Full mechanism detail for the cascade checks referenced from `SKILL.md` Step 1, excluding
C11 (`references/agent-security-c11.md`), C12 (delegates to
`skills/regulatory-trace/references/drift-check.md`), and C13
(`references/content-drift-c13.md`), which get their own files because of their size.

- **C4 — Validation invariants (sub-check, issue #761, escalated by #762).** Distinct
  from C4's own core "no Gherkin" gap in the checks table: for every `implemented`-status spec, check
  for a `## Validation` section (format: `docs/specs/README.md`). A test tagged with a
  scenario's name can pass while the spec's actual numeric/structural business rule
  (e.g. "C1 must be ≤ Addressable − Exclusions") goes completely untested — this
  sub-check is what catches that, distinct from C4's own scenario-presence gap and from
  C5's scenario→test mapping. Three outcomes, two severities:
  - **Missing entirely** → unchanged, still a `low`-severity WARN gap (`key:
    "C4:validation:<SPEC-NNN>"`, `found: "no ## Validation section"`) — a spec with no
    numeric/structural invariant to state has nothing to flag, so this never requires a
    `## Validation` section to exist, only that an `implemented` spec doesn't silently
    drop one it should credibly have. Advisory, same posture as every other check here.
  - **Present but no discoverable fixture/test run** → unchanged, still the same
    `low`-severity WARN gap, `found: "## Validation present but no covering fixture/test
    run"` — run `/sgd:spec-validate <spec> <fixture>` against the fixture its
    `<!-- validation:fixture -->` hint names (or the nearest
    `docs/specs/fixtures/<SPEC-NNN>*.json`, if that's the repo's layout) to check which
    case applies.
  - **Present, fixture found, and `/sgd:spec-validate` returns a failing/erroring
    invariant** → **escalated, not WARN.** Report this at `high` severity
    (`found: "## Validation invariant(s) fail against fixture — see
    /sgd:spec-validate output"`) and note in the finding that
    `platform/app/backend/scripts/validation-coverage-lint.ts`
    (`npm run lint:validation-coverage`, CI step `Validation-assertion coverage gate
    (sgd#762)`) already hard-fails this exact case in CI for this repo's own
    `docs/specs/*.md` — sgd-align's own posture stays advisory-only (it still never
    blocks a PR itself, per this skill's Role), but this specific sub-finding is no
    longer a soft nudge with nothing behind it; a real mechanical gate now backs it, and
    the finding should say so rather than reading as advisory-only prose.

- **C5 — scenario → test mapping.** A Gherkin scenario counts as *tested* if **any** of: a test (or `*.feature` step file) references its **scenario name**; a test carries a `@SPEC-NN` / `@scenario:<name>` tag matching it; or a BDD runner (pytest-bdd, cucumber) binds the `.feature` to a step module. Confirm the repo's binding convention in `CLAUDE.md`; if none is detectable, report C5 as **"convention unknown"** rather than flagging every scenario.

- **C9 — cross-repo mechanism.** Sibling repos and their contract paths are enumerated from the **fleet manifest** (`docs/sgd/fleet.yaml`, located in Step 0) — that file is the single source of truth for which repos this one shares contracts with. For each contract ref in a spec, fetch the upstream file at HEAD read-only via `gh api repos/<org>/<repo>/contents/<path> --jq .content | base64 -d` and compare against the spec's recorded schema/version/hash. No manifest → report C9 once as **"fleet manifest absent — C9 not checkable"** (a low-severity gap, not a crash).

- **C10 — L2 probe via atomic-audit.** Run `/sgd:atomic-audit` in `--json` mode (as a forked read-only subagent) and consume its `tier` as the L2 signal. **Disambiguation:** atomic-audit's L0–L3 are *adoption maturity tiers* (Ad-hoc → Enforced), **not** governance layers — record the gap as e.g. `found: "atomic maturity L1 (Emerging)"`, never as a bare "L1". Tier L2+/Established → pass. No detectable UI stack → C10 is N/A (excluded from scoring, noted in the summary).

- **C14 — TDD-evidence rate (process metric, issue #784).** Distinct from every other check: this measures *process* (did a test accompany the change) over a trailing window of merged PRs, not a point-in-time spec/code/test artefact link.

  **Mechanism — evaluate the SAME diff-based test-evidence check the CI gate uses, not merely the override trailer.** A trailer-only reading would be wrong in `advisory` mode: there a production-change / no-test / no-override PR merges on a warning yet would falsely count as `pass`, making the rate that feeds CISO/FCA/DORA reporting meaningless. So reconstruct the gate's own verdict per PR.

  `gh pr list --state merged --base <default branch> --limit 50 --json number,mergeCommit --search "merged:>=<window start>"` (a time-boxed window is preferred over a fixed count; either is fine — state which in the summary). For **each** merged PR, replay `require-test-evidence.yml`'s decision over its merge diff (`git diff <base>..<merge-commit-first-parent>` gives the same file set the gate saw), reusing this repo's `.sgd/test-map.yml` classification (production / test / exempt globs, `**`-aware) — do not re-implement the globbing loosely; it must agree with the workflow:
  - `pass` = the PR's diff touched **no production path**, **or** it paired at least one test-path change with its production change(s);
  - `fail` = the diff touched a production path with **no** test-path change **and** no commit on the PR carried the `^SGD-Override:\s*TDD;\s*.{10,}` trailer;
  - an **override-satisfied** PR (production change, no test, but a valid `SGD-Override: TDD;` trailer) counts as `pass` for the *rate* but is tallied **separately as an override** — report both `TDD-evidence rate = pass / (pass + fail)` **and** the override count, since a rate propped up by overrides is exactly the erosion `/sgd:drift-hillclimb` and the coherence trend must watch (same as ADR override trends).

  This definition is accurate in **both** `advisory` and `blocking` mode, because it measures the gate's *verdict on the diff*, not whether the gate happened to block the merge. (Fallback only if replaying the diff is genuinely infeasible in-session: report C14 as **N/A under advisory mode** with that reason stated — never silently substitute the trailer-only count, which over-reports the rate.)

  **N/A condition:** C14 is **excluded** (not scored, noted in the summary) when the repo has no `require-test-evidence.yml` workflow wired yet, or zero PRs merged in the window — nothing to measure. Never scored as 0% for an unwired gate; that would conflate "not adopted yet" with "adopted and failing."

  **Weight:** `×1` in the composite score, alongside C10–C12 (see the weights list below) — a process signal, not a spine/coverage check. **Cross-reference:** `/sgd:drift-hillclimb` restates these weights in its own Step 2 ranking — any change here must update that skill in the same PR.

- **C19 — Per-spec test coverage (SPEC-060).** The only check that measures test *substance*: a spec can pass C5 (a tagged test file exists) while the code it owns has 0% coverage — the `mapAgeCategory()` failure mode. C19 reads measured coverage per spec, not test-file presence.

  **Mechanism — consume the collector's verdict; never re-derive coverage in-session.** The single source of truth is `packages/coverage-collector` (`sgd-coverage check`, or `evaluateC19()` over a CI-published `coverage-by-spec.json` artefact). Locate the report: an explicit `--coverage-report <path>` first, else the repo's CI build artefact, else run `sgd-coverage collect` locally when a fresh reporter output (`coverage/coverage-final.json` / `coverage.xml`) already exists — never trigger a test run just to score this check. Each failing spec maps to the same `gaps[]` contract as C1–C14 with key `C19:<SPEC-NNN>`; thresholds come from `sgd-coverage-config.yaml` (default 70% lines). Unattributed source files above 20% of total instrumented lines are a **warn-level** finding (QD-02), never a fail; specs without `sourcePaths` are `N/A (not mapped)` — they are a mapping gap to *suggest*, not a coverage fail.

  **N/A condition:** C19 is **excluded** (not scored, noted in the summary) when no coverage report is locatable or no spec node in `docs/sgd-dag.json` carries `sourcePaths` — "not adopted yet" is never scored as 0%, same doctrine as C14.

  **Weight:** `×1` in the composite score for now (promote once sourcePaths backfill lands fleet-wide); the coverage *sub-score* the collector emits (`computeSm2CoverageSubScore` — per-spec coverage weighted by share of mapped source lines, SPEC-060 §3.4) is reported alongside the composite as its own line. **Cross-reference:** same lockstep rule as C14 — `/sgd:drift-hillclimb` restates these weights.

- **C20 — Docs coverage (parent #740).** The only check that measures whether the repo's governed artefacts are actually *documented*, aggregated as a single 0–100 coverage number that feeds the composite. The single source of truth is `bash ${CLAUDE_PLUGIN_ROOT}/skills/sgd-align/assets/check-docs-coverage.sh` (in non-fork invocations optionally wrapped in a forked read-only subagent — same pattern as C11/C12); consume its JSON, never re-derive coverage in-session. Its contract mirrors the C11 script exactly: read-only, JSON on stdout, exit `0` = fully covered or nothing to measure, `1` = ≥1 undocumented artefact, `2` = harness error; optional trusted repo-root as `$1`.

  **Definition (mechanical, file-only):** a **feature spec** is a git-tracked markdown file whose front-matter carries a `ref:` matching `SPEC-`/`SGD-`; it is *current-documented* iff it has a non-empty prose body **and** its `status:` is not `deprecated`/`superseded`/`retired`/`obsolete` (a stub or a retired doc is not current documentation). A **capability** is a `CAP-*` id declared with an `id:` key in a `capability-model.y*ml`; it is documented iff at least one current-documented spec cites it via front-matter `capability:`. `docsCoverage = round(100 × (documentedCaps + documentedSpecs) / (totalCaps + totalSpecs))`; `pass`/`fail` in the composite are the documented/undocumented artefact counts. **N/A** (excluded from the composite, noted in the summary) when the repo has neither a capability model nor any front-matter-bearing spec — "not adopted yet" is never scored as 0%, same doctrine as C14/C19.

  **Honesty note:** "current" here is the mechanically-verifiable signal (the doc exists, has real body, isn't retired-status). Deeper staleness — a doc older than the code it describes — is **C13's** job, not this file-only metric's; C20 never fabricates a freshness verdict it cannot see. Files without machine-readable front-matter aren't counted as governed specs (an honest, consistent denominator, never a silently-narrowed one). **Weight:** `×1` in the composite. **Cross-reference:** same lockstep rule as C14/C19 — `/sgd:drift-hillclimb` restates these weights.

- **C21 — UX/e2e coherence check (SPEC-078; unified id C34).** The user-journey analogue of C19: C19 proves a spec's *code* is exercised; C21 proves a *user-facing* Feature is exercised end-to-end. A Feature can be marked `built` in the capability model with **zero UX-level proof** the user journey works — presence in the model, no substance behind the journey. C21 keys off the existing Playwright infrastructure (`platform/app/frontend/e2e/*.spec.ts`, `e2e-real/`, BDD steps under `e2e/bdd/steps/`) — it **extends** those suites, never replaces them.

  **Eligibility — "absence is not a gap."** Only a Feature explicitly marked `user_facing: true` on its capability-model entry is in scope. A Feature without that marker is **skipped** (not flagged) — same doctrine as C13's eligibility test: a non-user-facing Feature has no user journey to prove, so its absence of an e2e scenario is not drift.

  **Mechanism — file-only tag match, no test run.** For each eligible Feature, scan the Playwright surface (`.spec.ts` under the e2e dirs above, plus `.feature` files) for at least one scenario **referencing the Feature's ID or any of its spec IDs** via the same `.feature` tag convention those files already use (`@SGD-049 @F-TRACEABILITY @cap:CAP-INTEGRITY-COHERENCE`, confirmed in `platform/features/integrity/SGD-049-bdd-traceability-harness.feature`) — i.e. a `@F-<ID>` or `@SPEC-NNN`/`@SGD-NNN` tag, or the bare id in a `test.describe`/scenario title. A Feature with no such reference raises one `gaps[]` record with the same contract as every other check: `check: "C21"`, `key: "C21:<F-ID>"`, `expected` (a tagged scenario), `found` (none). **Never trigger a Playwright run to score this check** — it is a tag-presence scan, the C19 doctrine ("consume evidence, don't re-derive it") applied to the e2e layer.

  **Severity — advisory, warn-only initially.** `high` for a `user_facing` Feature marked `built` with no scenario; `medium` for `building`. Per the catalogue (`packages/sgd-checks`, id **C34**) C21 ships **`advisory`** — it surfaces the finding and **does not block the merge**, following C19's advisory-then-enforce maturity ladder (SGD-027). A promotion-to-blocking decision is tracked (SPEC-078 §5), not assumed — mirrors C19's explicit-promotion discipline.

  **N/A condition:** C21 is **excluded** (not scored, noted in the summary) when the capability model marks **no** Feature `user_facing: true`, or the repo has no Playwright e2e surface at all — "not adopted yet" is never scored as 0%, same doctrine as C13/C14/C19/C20.

  **Weight:** `×1` in the composite (advisory checks never sit in the spine/coverage weight tiers). **Cross-reference:** same lockstep rule as C14/C19/C20 — `/sgd:drift-hillclimb` restates these weights; any change here updates that skill in the same PR. The unified catalogue (`packages/sgd-checks`) is the single source of truth for this check's id (C34) and severity tier.

- **C36 — Contract-testing (Pact) coherence check (SPEC-086; unified id C36).** The cross-service analogue of C19/C21: C19 proves a spec's *code* is exercised, C21 proves a *user journey* is exercised, C36 proves a spec's declared cross-service **contract** is exercised by a **real Pact consumer + provider pair**. A spec can describe a boundary *between* services and stay "green" while the two services would not actually interoperate — presence of a `contract:` declaration, no substance behind the verification. C36 keys off the same declarative mapping pattern C19 already consumes (a contract spec points at its committed pact file(s) the way a code spec points at `sourcePaths`), never a bespoke config surface (SPEC-086 OQ2 / the `@reuses-mapping-pattern` AC).

  **Eligibility — "absence is not a gap."** Only a spec that declares a non-empty `contract:` cross-service boundary is in scope. C36 defers to the enabler's applicability predicate (`packages/sgd-checks/lib/applicability/c36-contract.mjs` — `declaresContract`/`isApplicable`): a spec with no `contract:` field is **skipped** (not flagged) — same doctrine as C21's `user_facing` test. A boolean is honoured literally and an empty/whitespace-only string is not a boundary.

  **Mechanism — consume the enabler's gap-runner; never re-derive verification in-session.** The single source of truth is `packages/sgd-checks`'s **`runC36Gaps`** seam (SPEC-086, #1520) — the synchronous `(inputs) => gaps[]` runner exported from the package barrel (`@wealthtechpros/sgd-checks`). It resolves each spec's `contract:` front-matter via the shared declarative `implementations:`/`sourcePaths` mapping (`resolveContract`), loads the **committed pact JSON in-repo**, and verifies a real consumer + in-process provider pair against it — no broker, no network (SPEC-086 OQ3, ratified #1515). Wire it the same way this sweep consumes other package gap-runners (C19 consumes `packages/coverage-collector`'s `evaluateC19()`; C36 consumes `packages/sgd-checks`'s `runC36Gaps`): pass it as C36's runner into the SPEC-089 applicability evaluator — `evaluateApplicabilityChecks(inputs, { C36: runC36Gaps })` (`packages/sgd-checks/lib/applicability/runtime.mjs`) — so the eligibility gate and the gap logic compose: a repo with no `contract:` spec resolves C36 → N/A, a repo with ≥1 declares runs the real verification. **Do not re-implement verification here and do not edit `runtime.mjs`** (SPEC-089-owned) — the enabler deliberately exposed its own gap-runner precisely so this wiring consumes it without mutating the shared seam. Each unverified contract spec raises one `gaps[]` record with the identical contract as every other check: `check: "C36"`, `key: "C36:<SPEC-NNN>"`, `expected` (a passing consumer+provider verification against the committed pact), `found` (why it is a gap). **Never trigger a broker or network call to score this check** — committed pacts only, the C19 doctrine ("consume evidence, don't re-derive it") applied to the contract layer.

  **Severity — advisory, warn-only initially.** Per the catalogue (`packages/sgd-checks`, id **C36**, severity `advisory`) C36 **surfaces the finding and does not block the merge**, following C19's / C21's advisory-then-enforce maturity ladder (SGD-027). A promotion-to-blocking decision is a later decision (SPEC-086 §5), not assumed — mirrors C19's / C21's explicit-promotion discipline.

  **N/A condition:** C36 is **excluded** (not scored, noted in the summary) when **no** governed spec declares a `contract:` boundary — the applicability predicate resolves every candidate to N/A. "Not adopted yet" is never scored as 0%, same doctrine as C13/C14/C19/C20/C21.

  **Weight:** `×1` in the composite (advisory checks never sit in the spine/coverage weight tiers). **Cross-reference:** same lockstep rule as C14/C19/C20/C21 — `/sgd:drift-hillclimb` restates these weights; any change here updates that skill in the same PR. The unified catalogue (`packages/sgd-checks`) is the single source of truth for this check's id (C36) and severity tier.

- **C39 — Dual-authority precedence (SPEC-101; unified id C39).** The governance-completeness analogue of the platform's C16 *Canonical measure* check. C16 flags "one governed measure, more than one source"; C39 adds the follow-on governance question C16 stops short of: **has a precedence decision between the two authorities been recorded in an ADR?** The failure mode: a spec'd capability whose fact is derived by two live implementations (e.g. a persisted column *and* a live engine both deriving one value) with nothing recording which one wins — the ambiguity then sits as an "open design question" while the two sources drift apart. C39 catches it as advisory drift.

  **Eligibility — "absence is not a gap."** Only a single fact with **≥ 2 named authorities** is in scope. A single-authority fact is **skipped** (not flagged) — same doctrine as C21's `user_facing` test: no dual source, no precedence question, no drift.

  **Mechanism — file-only join of two signals already read, no new instrumentation.** C39 introduces no new per-repo config, marker requirement, or test run. It joins:
  1. **Candidate detection (dual authorities for one fact)**, in priority order: (a) the platform **C16** *Canonical measure* finding when the sweep carries it — a pre-computed "one measure, more than one source" signal C39 consumes directly (never re-derives, exactly as C19 consumes the collector and C38 consumes the DAG coverage layer); (b) **spec cross-refs** — two specs under the *same* capability whose derivation prose both claim to produce the *same* named value, or one spec whose implementation surfaces (`sourcePaths` / described derivations) name two distinct sources for one value, joined on the shared value name; (c) an **optional** author-declared `## Dual authorities` marker naming the `fact` + its two `source` authorities — a convenience, never required, and held to the same ADR requirement as an inferred dual source.
  2. **Precedence-ADR lookup** — for each candidate fact, scan `docs/decisions/*.md` (the L4 ADR layer already read for C7/C26) for an ADR that names **both** authorities *and* records which one is canonical / takes precedence. Such an ADR **suppresses** the finding — the dual source is then a documented, governed choice, not drift.

  A candidate with two authorities and **no** suppressing precedence ADR raises one `gaps[]` record: `check: "C39"`, `key: "C39:<capability-or-fact-id>"`, `expected` (an ADR recording precedence between the two authorities), `found` (`two authorities (<A>, <B>) derive <fact>; no precedence ADR`), and a **fixed, generic** `remediation`: *"Record precedence in an ADR (`docs/decisions/`) naming both authorities and which one is canonical."* The finding text names only generic terms (fact, authority, precedence, ADR) — **never** a client, repo, or company name. **Never re-derive a measure or trigger a run to score this check** — it is a cross-ref + ADR-presence scan, the C19 doctrine ("consume evidence, don't re-derive it") applied to the precedence layer.

  **Severity — advisory, warn-only initially.** Per the catalogue (`packages/sgd-checks`, id **C39**) C39 ships **`advisory`** — it surfaces the finding and **does not block the merge**, following C19's / C21's / C38's advisory-then-enforce maturity ladder. A promotion-to-blocking decision, and whether the "two sources" signal is scored via C16 or C39 (they must not double-count), are explicit later decisions (SPEC-101 §7 OQ2), not assumed.

  **N/A condition:** C39 is **excluded** (not scored, noted in the summary) when the repo has **no `docs/decisions/` ADR layer and no capability model** (nothing to join), or when **no candidate dual-authority fact is detectable** — "not adopted yet" / "nothing to check" is never scored as 0%, same doctrine as C10/C14/C19/C20/C21.

  **Weight:** `×1` in the composite (advisory checks never sit in the spine/coverage weight tiers). **Cross-reference:** same lockstep rule as C14/C19/C20/C21 — `/sgd:drift-hillclimb` restates these weights; any change here updates that skill in the same PR. The unified catalogue (`packages/sgd-checks`) is the single source of truth for this check's id (C39) and severity tier; its entry is added in the finalization step that also catalogues SPEC-091's C38 (keeps the `C1..Cn` line contiguous).

- **Composite coherence (0–100).** Weighted pass-rate across the checks that *apply* to this repo:
  `score = round( 100 × Σ(wₙ · passₙ) / Σ(wₙ) )`, where `passₙ = 1 − gapsₙ / applicableₙ` for check Cₙ. Default weights: coverage checks **C3, C4, C6 ×3**; spine checks **C1, C5, C13 ×2**; the rest (incl. C10, C11, C12, C14, C19, C20) **×1**. Checks whose layer is absent are excluded from both sums (and noted in the summary), so a missing layer lowers nothing it can't measure — C13 is excluded whenever no spec in the repo passes its eligibility test (no surviving path — nothing eligible to check), C14 is excluded whenever the test-evidence gate isn't wired or no PRs have merged in the window, C19 is excluded whenever no coverage report is locatable or no DAG spec node carries `sourcePaths`, C20 is excluded whenever the repo has neither a capability model nor a front-matter-bearing spec, and C21 is excluded whenever no Feature is marked `user_facing: true` (or there is no Playwright e2e surface), noted the same way. **This composite is the repo's Audit Score (AS) sample** (`audit_score`) — an operational fleet-audit rollup of per-check pass-rates, **not** SM-2. The single canonical SM-2 is the platform's `coherence_score` composite (SGD-032-S8 / #883), the org coherence score in the SGD Vision's Success Measures (decision #834).
