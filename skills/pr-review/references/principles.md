# PR Review — Key Principles (recap)

This is a consolidated recap of the merge-gate doctrine. Every principle here is the
enforced-in-the-phases rule stated once more as a checklist; the authoritative,
actionable form lives in the phase it names in `../SKILL.md`.

1. The PR must fully implement what the linked issue describes. Clean code with missing requirements = REQUEST_CHANGES. (Phase 4.1)
2. Any unaddressed previous review comment = flag it. (Phase 5.5)
3. Security issues in auth, token handling, or data isolation = BLOCKER. (Phase 6 table)
4. `pr-reviewed` is a merge gate, not a courtesy — only `pass` when the review actually passed (no Blockers) on a non-draft PR; withholding it is how REQUEST_CHANGES keeps the PR un-mergeable. (Phase 6/8)
5. `pr-reviewing` and `pr-reviewed` are mutually exclusive. Every transition goes through `${CLAUDE_PLUGIN_ROOT}/skills/pr-review/pr-labels.sh` — never edit these labels by hand.
6. A clean `pass` enables **auto-merge** in `default`/`--no-fix` modes; it still honours every branch-protection rule and never bypasses the gate. **`--no-automerge` (SPEC-090) promotes the gate identically but never arms auto-merge** — for a daemon/unattended dispatcher where the merge itself must stay a manual human step. (Phase 8)
7. Untraceable changes (no SPEC-NNN / capability linkage) are an **advisory** finding, not a blocker — the record is the SM-1 measure. (Phase 4.2)
8. **Fix safe, in-scope issues inline rather than commenting** (Phase 6.5) — security, bugs, types, lint; comments are for judgement calls and missing requirements. Never fix outside the PR's scope.
9. **All fixes happen in a worktree on the PR branch**, never the main workspace. Any push moves the head — re-pin `REVIEWED_HEAD` before promoting; the gate refuses a moved head so unreviewed commits can't slip through auto-merge. (Phase 6.5/8)
10. **`/sge:pr-review` owns the gate label; `/sge:pr-fix` owns CI-to-green.** Red CI → delegate (Phase 7), then promote; pr-fix never touches the label.
11. **Verify against head, never against intent** (issue #397). APPROVE only when every claimed-resolved finding is in the PR-head diff; a self-authored `--comment` verdict is still a gate decision. (Phase 5)
12. **Transaction atomicity is a standing review lens** (issue #397). Any multi-step database write (revoke-then-issue, delete-then-insert, debit-then-credit) must be atomic; a partially-applicable multi-step write is a Blocker, not a style note.
13. **Resolve every review thread before arming, not just your own findings** (Phase 5.5; issues #652, #717). A `required_review_thread_resolution` ruleset holds the merge invisibly; `pr-labels.sh pass` refuses while threads remain, and a failed thread query fails closed.
14. **Bound the wait on every Phase 2 agent; never nudge a stalled one indefinitely** (issue #686). ~10 min / 3 idle pings with no findings = stalled → re-dispatch fresh one-shot/fork and post an interim status.
15. **`--advisory` is review-only and is enforced, not requested** (issue #754). Skips gate claim, label transitions, direct-fix pushes, and promote; `SGE_REVIEW_ADVISORY=1` makes `pr-labels.sh pass` refuse (exit 4). `--no-fix` owns the gate but never pushes a fix. **`--no-automerge` (SPEC-090) owns the gate and fixes inline exactly like `default` — it only omits `--auto-merge` from the Phase 8 promote call**, so the merge itself always stays a manual step (the daemon use case this mode exists for).
16. **A declared follow-up must have a durable home before the gate opens** (issue #859). A "follow-up"/"deferred"/"future PR" item in the PR body or review text with no issue reference evaporates when the linked issue auto-closes on merge; `pr-labels.sh pass` refuses (exit 6) until each references a filed issue — file it first, as the manual #847 remediation did.
17. **A PR from a rescued/resumed worktree gets its quality gates re-run, never inherited** (issue #951). A stale or junctioned build makes the author's `tsc`/test claims untrustworthy; when `RESCUED_ENV=1` (or the body doesn't attest an isolated environment), re-run Phase 3 here, and run `../worktrees/rescue-guard.sh` against any fix worktree before trusting your own re-runs. Once a check is dispatched to a lane, wait for its verdict — don't shadow-verify the same thing in parallel.
18a. **Claim the gate FIRST, and fix what you find — both are enforced, not requested** (issue #981). `start-review` (apply `pr-reviewing`) is the unskippable first step even in an adapted flow: `pr-labels.sh pass` refuses (exit 7) to promote a PR that carries neither label, so there is no "no label → `pr-reviewed`" jump and the #699 guard always gets its claim (`--skip-claim-check` bypasses loudly). And Phase 6.5 is the DEFAULT continuation of Phase 5 — every "fix inline" finding is fixed before Phase 8, never reported-and-parked for the operator to re-ask.
18. **Review cost must scale with diff risk, and reuse free signal before paying for more** (issue #688). Low risk + clean bot review skips fresh dispatch; only security-sensitive diffs always get full treatment; Phase 2 is budgeted, and a budget-exhausted lane is reported as partial, never treated as clean. Bot findings feed the same structured pipeline. A provably non-semantic diff (`trivial` tier, issue #973 — whitespace-only, or a single-file lockfile bump with a passing check) skips specialist dispatch outright, with no bot-review precondition; Phase 3/4/5.5 still run in full regardless of tier.
