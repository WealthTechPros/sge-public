# Behavioural verification tier — control-bearing changes (issue #2211)

**Reading a diff is not reviewing it when the diff IS a control.** The measured gap: the same PR reviewed twice — a read-the-diff pass approved it with minor observations; an execute-it pass built a bypass corpus and found 26 of 30 constructed bypasses succeeded, plus a fail-open a third reviewer reproduced by constructing the triggering condition natively. `DIFF_RISK` alone does not catch this: `rl_security_glob_regex` flags security-sensitive *content* (auth/secrets/config), not "this file IS a gate/checker/audit script" — a diff can sail through as `low`/`medium` risk while quietly defanging the thing that is supposed to catch exactly that.

```bash
CONTROL_BEARING=$(rl_diff_control_bearing "$PR")   # 1|0, issue #2211 ask 1
```

**`CONTROL_BEARING=1`** (mixed-diff trigger — one control-bearing file among many still fires, unlike `prose`'s all-files rule) escalates regardless of `DIFF_RISK`'s own tier: this is a **selected** tier per the issue's own scope note (doc-only/prose changes never need it — `rl_diff_control_bearing` and `rl_diff_prose` are mutually exclusive in practice since the control-bearing glob excludes markdown), not a blanket requirement on every PR.

**What escalation means — delegate to `/sge:qa-audit`, don't reimplement it.** `qa-audit` already owns the exact execution shape this needs: isolated worktree, running build, posts evidence, no gate labels, `context: fork` (safe to background). Reimplementing "plant a violation and observe the failure" inside `pr-review`'s own Phase 2 fan-out would duplicate that harness. So Phase 2 dispatches `/sge:qa-audit "$PR" --adversarial` (issue #2211's asks 2–5 — attempt to defeat the control, a negative control, non-vacuous test assertions, and a pre-change-revision run — are that flag's contract, documented in `qa-audit`'s own SKILL.md) **in addition to** the normal Layer 1–3 review, never instead of it: the adversarial pass proves the control still works at runtime; the normal review still catches everything else (unrelated bugs, style, requirements). Both run; Phase 4.3 blocks on the adversarial report the same way it already blocks on a stale/absent QA report.

**Phase 4.3 gate extension.** For a `CONTROL_BEARING=1` PR, `qa_evidence: none` or a `--adversarial` report that is stale/absent is a **BLOCKER**, not the existing advisory-only treatment — the whole point of this tier is that a clean code-review pass alone is not sufficient evidence for a control-bearing change. See Phase 4.3 in SKILL.md.

**4.3a Adversarial evidence — mandatory for control-bearing changes (issue #2211).** When Phase 2's `CONTROL_BEARING=1`, the optional dispatch above becomes **mandatory**, and `qa_evidence: none` or `stale@*` is a **BLOCKER** (`{severity:"blocker", category:"security", finding:"control-bearing change with no current adversarial evidence — reading the diff does not verify the control still works"}`), not the advisory treatment 4.3 gives every other tier. A current adversarial report is verified for its **negative-control result**: `qa-audit --adversarial`'s report must show at least one constructed bypass/violation that FAILED against the change (the control caught it) — a report showing every attempted bypass succeeding is itself the finding (ask 3: "if the reviewer cannot make the check fail, that's a finding, not a pass") and downgrades the PR to REQUEST_CHANGES regardless of how clean the rest of the review reads.

Record `control_bearing: true | false` in the verdict block.
