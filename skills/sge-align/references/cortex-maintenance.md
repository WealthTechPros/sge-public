# Step 6 — Cortex maintenance (Layer 8 distillation)

Full mechanism for Step 6, referenced from `SKILL.md`. Read this before running Step 6.

Cortex (L8, `docs-site/what-is-sge/cortex.md`) accumulates raw, episodic entities during ordinary sessions elsewhere in this plugin (`search_nodes`/`create_entities` in `/sge:sge-implement` Phase 0, `/sge:sge-preflight` Step 0, etc.), but the `consolidate`/`reflect` tools that distill those into reusable, derived "pattern" memories were never called from anywhere (#678). `/sge:sge-align` is already the periodic, whole-repo governance sweep, so it is the natural, low-cost place to trigger that distillation rather than standing up a second scheduled job — this is maintenance, not a check: it never raises a `gaps[]` record, is never scored, and runs regardless of `--dry-run` (it never touches a GitHub issue, only this repo's own local Cortex db).

**Runs:** at the end of every full sweep (default mode and `--apply`), and inside each per-repo fleet audit agent (Fleet mode) — a fleet agent stays read-only *on GitHub* but this step only writes to that repo's own `memory/sge-memory.db`, so it doesn't violate the fleet agents' no-issue-mutation contract. **Skipped** in the standalone `--dimension agent-security` / `--dimension regulatory` / `--dimension skill-quality` modes, which intentionally run only their one dimension for speed.

**Agent-side distillation (in-context) — every run, and this is the one that actually improves recall.** The `consolidate`/`reflect` tools (items 1–2) only write to the `derivatives` table, which **no retrieval path reads** — and the Cortex server is deliberately no-egress, so it can never distill in-server. Real distillation therefore happens **here, in your context**, and is written back as ordinary searchable nodes:

1. **Read the raw graph.** Call `read_graph` (or a few targeted `search_nodes` queries over this repo's active scope). Skip silently — no gap, no error — if sge-memory is unavailable (same soft-unavailable convention as elsewhere in this plugin). A near-empty graph is a graceful no-op: report `Cortex: nothing to distill` and move on.
2. **Distill cross-issue patterns in-context.** Identify recurring lessons that span ≥ 2 episodic entities (e.g. the same gotcha hit in two issues, a convention re-derived repeatedly). Ignore one-off, issue-specific caches — those stay episodic.
3. **Write each back as a first-class, searchable entity** via `create_entities`, using a **durable** `entityType` of exactly `pattern`, `convention`, or `gotcha` (the taxonomy the recency/TTL rules in `store.ts` treat as durable), a stable descriptive `name`, and observations stating the lesson + the issues it was distilled from. These are the entities a future `search_nodes` (now AND-biased and `entityType`-filterable, #731) will actually return — this is what lifts recall above the ~9% baseline. Report `Cortex: distilled N pattern/convention/gotcha entities`.

Only after this in-context pass do the two tool-driven maintenance calls run:
<!-- END #731 agent-side distillation -->

1. **`consolidate` — every run.** Call the `consolidate` tool (sge-memory MCP; **skip silently, no gap, no error** if sge-memory is not configured/available in this session — the same soft-unavailable convention `search_nodes`/`create_entities` already use elsewhere in this plugin). It returns `null` when the repo's Cortex db has no raw nodes yet (or none in the active scope) — that is the **graceful no-op** required by #678, not a failure; report `Cortex: no data to consolidate` and move on. A non-null result means one derivative row was written per active scope — record its `id` / `scope` / input-node count.
2. **`reflect` — weekly cadence, self-timed off the audit log (no new state file needed).** Reflect is heavier (cross-context reasoning) than consolidate, so it shouldn't run every sweep. Call `audit_read` (no `scope` filter, `limit: 1000`) first — it returns entries **oldest-first**, so the most recent `op: "reflect"` row, if any, is whichever such row appears **last** in the returned array. If none exists, or its `ts` is **≥ 7 days** old, call `reflect` (`crossContext: true` only when this sweep is itself part of a `--fleet` run spanning ≥ 3 repos — mirroring Cortex's own cross-repo-elevation threshold from `docs-site/what-is-sge/cortex.md`, a policy choice made here, not something `reflect()` enforces itself — otherwise plain `reflect`), then report it the same way as `consolidate`. Otherwise skip it and note `Cortex: reflect last ran <ts>, not due`. **Known limitation:** `audit_read`'s 1000-row cap has no offset/newest-first option, so once a single repo's Cortex audit log exceeds 1000 total rows (writes from every `consolidate`/`reflect`/`delete_scope` call, not just this step — realistically years away at a weekly cadence) the oldest 1000 rows returned may no longer include the true most-recent `reflect` entry, and this cadence check would over-fire rather than silently under-fire. Treat over-firing (occasionally running `reflect` sooner than weekly) as the safe failure mode; if this ever becomes a real problem, add an offset or newest-first option to `audit_read` rather than working around it here.
3. **Never fails the sweep.** Any Cortex error (MCP not configured, db locked, etc.) is caught and logged as one summary line (`Cortex: unavailable — <reason>`) — it never raises a drift gap, never blocks Steps 0–5, and never fails the run.

Add one line to the Step 5 scorecard (not a `checks[]` entry — this is maintenance, not a coherence check):
